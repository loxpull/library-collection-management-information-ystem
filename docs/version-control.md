# 16. Правила ведения репозитория

Для проекта информационной системы управления библиотечным фондом предлагается следующая схема ветвления:

```text
main
develop
feature/*
fix/*
docs/*
```

## 16.1. Ветка main

Содержит стабильную версию проекта. Изменения попадают в эту ветку после проверки.

## 16.2. Ветка develop

Используется для объединения результатов разработки перед включением в стабильную версию. Для небольшого индивидуального проекта схема может быть упрощена до основной и рабочих веток.

## 16.3. Ветки feature/*

Используются для разработки новых функций.

Примеры:

```text
feature/book-catalog
feature/copy-inventory
feature/reader-management
feature/loan-workflow
feature/library-reports
```

## 16.4. Ветки fix/*

Используются для исправления дефектов.

Примеры:

```text
fix/copy-availability
fix/loan-return-date
fix/reader-validation
```

## 16.5. Ветки docs/*

Используются для изменений документации.

Примеры:

```text
docs/project-scope
docs/api-contracts
docs/architecture
```

# 17. Правила коммитов

Один коммит должен содержать одно логически завершенное изменение.

Используются следующие префиксы:

```text
feat: новая функциональность
fix: исправление дефекта
docs: изменение документации
test: добавление или изменение тестов
refactor: изменение структуры кода без изменения поведения
chore: техническое обслуживание проекта
```

Примеры сообщений:

```text
docs: add library project scope
docs: add architecture diagram
feat: add book catalog
feat: add reader management
feat: add loan workflow
test: add copy availability tests
chore: add gitignore and editorconfig
```

## 17.1. Проверка перед коммитом

Перед фиксацией изменений необходимо:

1. выполнить `git status`;
2. проверить список измененных файлов;
3. убедиться, что временные файлы не попадают в репозиторий;
4. проверить отсутствие паролей и токенов;
5. выполнить доступные тесты;
6. создать коммит с понятным сообщением.

## 17.2. Слияние изменений

Перед слиянием рабочей ветки необходимо проверить актуальность изменений, просмотреть различия файлов и выполнить доступные тесты.

При возникновении конфликтов следует согласовать изменения, проверить итоговые файлы и только затем завершить слияние.

## 17.3. Игнорирование файлов и секреты

Правила исключения файлов должны находиться в `.gitignore`.

В репозиторий не следует добавлять локальные настройки, временные результаты сборки, пароли, токены и строки подключения с секретными данными.

Если секрет уже был опубликован, необходимо отозвать или заменить его. Удаление файла из последнего коммита не удаляет его из предыдущих версий истории Git.

## 17.4. Контрольное состояние

Для обозначения проверенного состояния проекта можно использовать аннотированный тег:

```bash
git tag -a v1.0.0 -m "Library project checkpoint"
```
